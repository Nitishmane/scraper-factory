Scraper.Factory Story Architecture Workforce Platform

The platform underneath

Three products carry the weight: Port is the control plane, SigNoz is the telemetry, and Bright Data is the scraping. Everything here is provisioned as code — scripts/bootstrap_port.py and scripts/bootstrap_signoz.py are idempotent and re-runnable, with one documented UI step left over.

Port — the control plane, pillar by pillar

📚Catalog

Seven blueprints model the whole factory: data_source, scraper, scrape_run, heal_event, ranked_title, requirement, and factory_deployment — plus two service entities.

🌊Context Lake

The product itself lives here: 20 ranked_title entities (show_01..10, movie_01..10). The webapp reads them server-side — the same lake the operator dashboard and the AI agents see.

🎛️Actions

Self-service: request_data_source (brief → verified scraper), submit_feature_request (requirement → PR via the local builder), and the operate-now buttons run_scrape_now / refresh_catalog_now / publish_now.

⚡Automations & Workflows

invoke_healer_on_drift (drift → /heal); scheduled wf_scheduled_scrape (08:00 UTC → /run) and wf_scheduled_catalog (07:30 → /catalog); event wf_publish_on_success and wf_heal_on_bad_run. Port operates the factory (see below).

🏅Scorecards

scraper_reliability: Basic → Bronze (verified today) → Silver (verify passing) → Gold (healthy + verified). Computed from properties the pipeline writes — trust as data.

🖥️Dashboards

Factory Operator: a scrapers-by-health pie, a heal-event table, a ranked-titles table with record links, an architecture note, and the embedded SigNoz dashboard.

🤖AI agents

Four factory agents — Triage, Heal Explainer, On-Call Assistant, Catalog Coverage — registered as _ai_agent entities. See the workforce page.

⚙️All as code

bootstrap_port.py creates every blueprint, action, automation, scorecard, dashboard, and agent above — idempotent, no UI clicks, validated against the live api.getport.io.

Port operates the factory

Port doesn't just catalogue the factory — it runs it. Scheduled and event workflows POST to the FastAPI service, which does the work in the background and returns 202 at once. make run and friends stay as dev conveniences.

Port triggerWhenCalls
wf_scheduled_catalogdaily 07:30 UTC (cron)POST /catalog — refresh the record-URL map
wf_scheduled_scrapedaily 08:00 UTC (cron)POST /run — scrape the guide, all providers
wf_publish_on_successa scrape_run lands status = successPOST /publish — push the ranking to the Context Lake
wf_heal_on_bad_runa scrape_run lands status = error / driftPOST /heal — Triage authors the drift description
run_scrape_now / refresh_catalog_now / publish_nowoperator presses a buttonsame endpoints, on demand

Endpoints POST /run, /catalog, /publish each return 202 and run as background tasks, so a Port call never blocks on a scrape. And failures are now visible in Port: scrape_run entities record status = "error" plus an error_detail field carrying Bright Data's actual error text, so wf_heal_on_bad_run can react and the dashboard shows why a run failed — previously a failed run simply produced no rows and was invisible.

Webhook auth. All six POST endpoints (/run /catalog /publish /heal /feature /build) are gated by a shared secret FACTORY_WEBHOOK_TOKEN, carried as ?token= or an x-factory-token header and compared in constant time; a bad or missing token returns 401. The bootstrap scripts bake the token into every provisioned Port + SigNoz webhook URL (SigNoz can't send headers, so it rides in the query string). GET routes — the demo site at /, /top20, /api/top20, /healthz, /docs — stay open. If /heal gets a payload with unresolved fields, it resolves the newest bad scrape_run from the Context Lake itself.

Two pull bridges. Most signals are pushed by the pipeline as it runs, but Port's control-plane activity and Bright Data's account budget aren't things those systems push anywhere — so the factory polls them. A background watcher (portwatch.py, started with the API) reads Port's action-run and workflow-run listings on an interval and re-emits each new run as the port.action.runs / port.workflow.runs counters, and it samples brightdata budget into the brightdata.budget.remaining gauge. Both drive their own dashboard panels; new runs are de-duplicated in SQLite so a restart never double-counts.

Bright Data — collectors, healing, and the relay

The policy that shaped the design: Bright Data blocks collector runs against streaming-media domains (confirmed and endorsed by their support, 2026-08-22). So production scraping is a fetch/extract split: the Web Unlocker fetches the live page and archives it, and the collector extracts from a tunneled copy in fixtures/relay/. The code retries a direct run first, so if the policy ever lifts the relay drops out on its own. See diagram 2 on the architecture page.
